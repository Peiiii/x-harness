# Batch discovery
For a batch of active replies, first use `x.discoverReplyCandidates({queries:["互关 min_faves:20", "串门 min_faves:20"],target:20,processedIds})`. One call owns serial paginated searches, original-ledger target/author exclusion, deduplication and deterministic age/likes/language/body gates. It performs no writes. Save/reuse `examinedIds` on the original actor; full candidate text, original per-window proofs and the combined proof stay available locally. `requiresReview:true` means relevance, human identity and suitable text still need review. Review the batch, then use existing `replyBatch`; do not rebuild per-person discovery or infer approval from metadata. Partial shortages include rejection totals and window warnings; `pageComplete:false` never claims all of X was read. Night boundary stops further reads. Missing metrics remain unknown. Repair a concrete missing capability at its original owner, validate it and resume the task; no source reading for normal calls. Refill the saved queue through this API; tool maintenance never replaces execution.

The SDK defaults to `minLikes:20` when omitted. For a policy with no likes gate, use `x.discoverReplyCandidates({queries:["互关 -filter:replies"],target:3,minLikes:null,processedIds})`; do not keep a `min_faves` filter in that query. Explicit null disables only likes qualification, including for missing counts, without inventing metrics. Numeric zero still requires a measured count. Other qualification and semantic review remain mandatory.

Consecutive windows continue the confirmed exact search query without reopening its top; finish that bounded query before switching. Standalone `searchSources({query,resume:true,...window})` refuses a different current route/query. Resume does not bypass freshness, alerts or night gates.

## Author identity in source cards

Recommendation source cards include optional `authorIdentity` in the same read: exact author handle/name/profileURL and `blue:true` only with the matching visible blue badge. The source proof covers it; no profile navigation is added. Missing/ambiguous/generic badges remain `blue:null` with missing reasons. This does not establish biography, personal identity or inbound relationship; review current post semantics, and only supplement genuinely missing qualification evidence.

## Follow candidates from a people list

Use `x.discoverFollowCandidates({target:{url,evidenceRef},maxWindows:20,terms:["AI","人工智能"],requireBlue:true,excludedHandles})`. One bounded read-only call advances list windows, consumes DOM offsets, deduplicates handles and returns only rows with an observed `not-following` control. It stops on two stalled windows, unconfirmed reads, the window budget or the night boundary. Each candidate retains its original window evidence; `complete:false` means the whole list was not proven. `terms` are optional, case-insensitive OR matches on biography; omitted terms allow other topics. A list row does not prove follower/following counts, recent activity, reciprocity or permission to follow: review those through original business evidence and preserve unresolved original actions. Never treat a match as automatic approval or a missing row as evidence of absence.
