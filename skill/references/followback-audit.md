# Followback list audit

`x.readFollowbackAudit({following,followers,maxWindows?,scanId?,nightReadAuthorization?})` reads lists only. Each target is `{url,evidenceRef,expectedCount?}` from the same observed account profile: following and **unfiltered** followers URLs, exact counters only. `verified_followers` is a subset and is rejected. A missing/rounded counter cannot establish full coverage. No profile-per-person opening, follow or unfollow is performed.

One call scans bulk visible rows (up to 100 per observation) and serially advances the original list; no model-driven five-person loop. maxWindows defaults to 100 per list, range 1–1000. The same instance can resume via scanId with identical targets. Preserve that binding: a new instance cannot restore the in-memory job and must restart conservatively. Full immutable observations and checkpoint go to the existing proof directory; the receipt gives counts, completeness and evidenceRef. Read that local proof for lists or export it without dumping all rows into model context.

Proof arrays: `mutual`, `nonFollowers` (we follow, they do not), `notFollowedBack` (they follow, we do not), `provisional` (following entries absent from incomplete followers). `notFollowedBack` requires count-matched following coverage; nonFollowers requires count-matched unfiltered followers. Never treat provisional as confirmed negative. Only both count-matched lists produce complete:true. Counts can change while scanning; the result is an observation interval, not an atomic or permanent relationship guarantee. Check exact relationship again before any write.

Alerts, wrong routes, unreadable rows, stall and window exhaustion retain incomplete proof; resume without assuming a virtualized tail means all. Missing own following controls remain a coverage gap. Shanghai 00–07 stops each new window. Only explicit human permission for this task/time can set `nightReadAuthorization:{userAuthorized:true,evidenceRef,expiresAt}` with an existing local user-authorization proof; this permits this audit's reads only, never writes or other tasks. It is not an SDK-wide technical lock.

To actually follow back, load the matching writes reference, review candidates under the original project authorization, register original stable IDs, and use followBatch. This audit grants no relationship-write permission or quota exemption.
